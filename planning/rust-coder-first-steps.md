## Hardest Parts to Build (Risks & Challenges)

1. **Safe, bounded self-modification and GapFind decisions** (highest risk):
   - GapFind proposing bad splits or infinite specialization (e.g., over-fragmenting into useless micro-agents).
   - Ensuring meshing doesn't introduce subtle Rust unsoundness (e.g., wrong Send bounds).
   - Mitigation: heavy use of review_file + plan_mode for all self-changes; parent (human or main Grok) veto; metrics thresholds before split; "max evolution" detection with data (not just LLM guess).

2. **Persistent state, resumption, and cross-session identity**:
   - Durable scheduler + STATE.md loading must work perfectly after restarts/compaction.
   - Git subtree management for inheritance on splits (no duplication, correct attribution).
   - The agent's "self" (IDENTITY + pack) must evolve without losing history.

3. **Rust toolchain and isolated execution in this env**:
   - No Rust installed currently. Agent must reliably set up clean Rust envs (rustup in worktree? docker run --rm rust:slim for tests?).
   - Cargo can be slow/noisy; need good timeouts, output filtering via monitor.
   - Handling different Rust editions, nightly for some features, dependency hell in tests.

4. **Effective meshing for Rust + general skills**:
   - Rust has very specific idioms (ownership, lifetimes, async traits) that don't mesh trivially with generic "implementer" persona.
   - Detecting real synergies vs. superficial (e.g., "use thiserror in all errors" must be enforced across meshed skills).
   - Testing meshes for Rust is non-trivial (need real compilable projects that exercise the mesh).

5. **Recursive splitting and multi-agent coordination**:
   - Managing the tree of child agents (scheduling, meshing their outputs back for vast tasks, avoiding duplication of effort).
   - "Unidentified" bootstrap working without a human-defined focus.
   - Depth limits on subagents; preventing explosion of specialists.

6. **Performance and observability of the loop**:
   - Loops must be bounded (time, tokens, acquisitions per cycle) or it will be expensive/unusable.
   - Good metrics for "evolution maxed" and "mesh quality" (hard to quantify for code quality).
   - Logging the GapFind "why this agent type?" decisions so they are auditable.

7. **Bootstrap and cold-start for a new focus like Rust**:
   - Initially no skills, so first Acquire relies on web + general knowledge. Risk of hallucinated Rust patterns.
   - Getting the first "meshed pack" to a useful state quickly.

8. **Integration complexity with existing Grok**:
   - The sustaining agent must be spawnable via the normal `spawn_subagent` without breaking the parent's context.
   - Meshing must not pollute global skills (keep everything under the focus subtree, activate by prompt injection).

## Software, Apps, Tools to Integrate or Build

**Core (already available or easy via terminal)**:
- Rust ecosystem: rustup (installer script), cargo, rustc, rustfmt, clippy, cargo-test, cargo-clippy, cargo-expand (for macros), cargo-audit (security), cargo-tarpaulin or llvm-cov for coverage.
- Git (subtree commits, worktrees for isolation and testing).
- The Grok TUI primitives: scheduler (for sustaining triggers), run_terminal_command (the "shell" for cargo/rustup/git), spawn_subagent + worktree isolation, todo_write, plan_mode, web tools (for crates.io search, docs.rs), create-skill (for the agent to birth new Rust skills).
- Existing bundled skills (implement/design/review/create-skill) for the agent's self-improvement loops on its own pack.
- `bin/update-mem-context.sh` cron (for auto git push of the agent's learned artifacts).

**To Build (in this repo, as part of the agent's pack or infrastructure)**:
- Custom Rust domain skills and personas (as listed in "Skills Needed").
- The sustaining-orchestrator (as SKILL.md or prompt file per focus, with GapFind + meshing logic).
- Testing harness: `testing/harness/rust-mesh-tester.sh` or SKILL.md (sets up cargo project in worktree, runs the meshed skills via injected prompts + cargo commands, collects review outputs + cargo test results).
- Gap-finder implementation (prompts + helper script that scores "agent type mesh targets").
- STATE.md / IDENTITY.md schemas and loaders (simple markdown + perhaps a small python parser if needed for the orchestrator).
- Meshing utilities: scripts to auto-generate cross-refs or check compatibility (e.g., "does this new async skill use the same error type as existing?").
- Performance/metrics collector for Rust (parse cargo test output, clippy warnings count, etc. into jsonl).
- Possibly a small "rust-coder" modpack manifest (MODPACK.md + activation snippet).

**External/Optional Integrations (via web or terminal)**:
- crates.io / docs.rs / lib.rs (via web_search/fetch for discovering crates and patterns).
- Rust RFCs, Rustonomicon, "Rust for Rustaceans" book excerpts (web).
- If the env supports: Docker for clean `docker run --rm -v $PWD:/app -w /app rust:1.XX cargo ...` (highly recommended for isolation and reproducibility of Rust envs; avoids polluting host or dealing with rustup in every worktree).
- cargo tools: install via the agent itself in test envs (cargo install cargo-nextest, cargo-machete, etc.).
- For "full apps": nothing heavy like a full Rust IDE (rust-analyzer can be used via terminal if installed, but not required). Focus on CLI cargo + the agent's own skills for code gen/review.
- GitHub (if we add pr-babysit integration for Rust PRs generated by the agent).
- Future: perhaps a simple web UI or MCP server for viewing the agent's current pack / improvement log, but start minimal (use existing TUI + cat/grep on the files).

**What we will *not* integrate initially**:
- Heavy external Rust tools beyond cargo/rustup (e.g., no full VSCode).
- New languages or unrelated (keep laser-focused on Rust for this test).
- Persistent databases beyond git + markdown files (unless a simple SQLite for STATE if markdown becomes unwieldy; but start with files as per architecture).

**Bootstrap assumption**: The first runs may require the parent (human/Grok) to help with initial Rust toolchain setup in a test worktree, or provide seed knowledge. The agent then takes over acquisition/meshing.

This setup reuses ~90% of existing Grok power. The "new" parts are domain-specific content (Rust skills) + the orchestrator glue + the testing harness tailored to cargo/Rust + the GapFind logic for specialization.

Once the rust-coder focus is bootstrapped and one loop runs end-to-end (acquire a simple pattern like "Result handling", mesh it with general implement, test via cargo in worktree, GapFind proposes e.g. "async-result" sub-type), we can evaluate and iterate on the architecture.

All planning and code will live here and be pushed.
